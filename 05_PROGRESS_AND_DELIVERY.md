# 05 — Максимальная обработка, контрольные точки и доставка ZIP

## Главный принцип

После команды «Начинай» выполнять максимально возможный безопасный объём работы за один запуск, исходя из **реально доступных** инструментов, ресурсов и времени. Нет обязательного лимита «50 страниц на ответ». Однако должен сохраняться запас для записи результатов, проверки ZIP и ответа. ChatGPT не может увеличить выделенные ресурсы, выполнить бесконечную фоновую задачу или автоматически продолжить без нового запроса.

## Контрольные точки

1. Перед первой правкой зафиксировать SHA-256 исходника, размер, количество страниц, режимы/языки, версию управляющих правил `1.1.0`.
2. Делить тяжёлую работу на независимые проверяемые блоки; блоки могут включать 50–100 страниц либо иное число по результатам измерений.
3. После успешного блока сохранить его результат и контрольную сумму, добавить информацию в `progress.json` и `report.md`.
4. Указывать **реально проверенные** состояния: `not_started`, `processing`, `done_verified`, `needs_review`, `failed`. Не записывать `done_verified` до проверки.
5. При угрозе лимита времени/памяти остановить запуск новых тяжёлых блоков, безопасно завершить начатое, упаковать доступные результаты.
6. Упаковать готовые части вместе с отчётом, инструкцией по возобновлению и состоянием, проверить CRC/читаемость архива и существование его содержимого.
7. Если книга завершена, собрать целый PDF, выполнить проверки из `03_QUALITY_AND_TOC.md`, затем создать и перепроверить финальный паспорт BookScan/единственную безопасную метку, вычислить внешний `final_sha256` и передать **только финальный ZIP**.

## Содержимое промежуточного архива

```text
book_progress_001.zip
  /parts/pages_0001-0100.pdf           # только фактически выполненные диапазоны
  /parts/pages_0101-0200.pdf
  progress.json                         # машина-читаемое состояние
  report.md                             # человекочитаемый статус и проблемы
  toc_plan.json                         # распознанные разделы/план закладок, если готов
  RESUME.md                             # как продолжить, что приложить
  PROPOSED_UPDATE.md                    # только если найдено проверенное новое решение
```

Если обработка — глобальный ремонт шрифтов без удобного разбиения по страницам, сохранять **целостную проверенную промежуточную копию PDF + журнал транзакций**, а не искусственно создавать сотню фрагментов. Не писать в архив файл, которого реально нет.

Не обязательно добавлять исходник в каждый ZIP, если он уже доступен пользователю и слишком велик. Но в `RESUME.md` прямо указывать, нужен ли повторный исходный PDF. Для возобновления в новом чате обычно понадобятся **архив прогресса + исходный PDF**.

## Обязательные поля состояния (пример структуры)

```json
{
  "schema_version": 1,
  "project_rules_version": "1.1.0",
  "source_file_name": "book.pdf",
  "source_sha256": "<real SHA-256, not a placeholder in working state>",
  "source_page_count": 500,
  "page_numbering": "pdf-1-based-inclusive",
  "method": "mixed/A-B-C-D",
  "completed_ranges": [{"from": 1, "to": 100, "status": "done_verified", "file": "parts/pages_0001-0100.pdf", "sha256": "<real SHA-256>"}],
  "pending_ranges": [{"from": 101, "to": 500}],
  "warnings": [],
  "toc_status": "planned",
  "created_by_run": 1
}
```

`<...>` здесь — поясняющий шаблон; в реальном состоянии недопустимы фиктивные значения. Диапазоны страниц **включительные, нумерация с 1**, не путать с нулевой индексацией библиотек. При иной нумерации явно документировать преобразование. Статусы в JSON — не «память ChatGPT», а проверяемые сведения о сохранённых файлах.

## Возобновление по команде «Продолжай»

1. Найти фактически доступный исходник и последний ZIP/файлы из предыдущего запуска. Если недоступны — запросить необходимые вложения, не обещать восстановить невидимый файл из прошлой сессии.
2. Проверить SHA-256 исходного PDF, схему `progress.json`, номера страниц, пересечения/дыры в диапазонах, наличие и SHA-256 частей.
3. Проверить совместимость настроек и версии инструкций; при изменении версии описать миграцию.
4. Пропускать только файлы со статусом `done_verified` и подтверждённой целостностью. Повреждённые/сомнительные блоки перепроверять или пересоздавать.
5. Продолжить с первого невыполненного блока. Если серия исправлений зависит от общей карты шрифтов, загрузить и проверить карту перед продолжением.
6. По окончании повторно выполнить сборку, финальные проверки текста, ссылок и содержания.

## Финальный архив

```text
book_final.zip
  book_corrected.pdf
  report.md                         # содержит final_sha256, паспорт и статус метки
  PROPOSED_UPDATE.md        # если есть новое проверенное открытие
```

Можно включить дополнительный TXT/JSON с текстом или диагностикой только если пользователь просил либо это помогает дальнейшей проверке; не загромождать архив множеством временных файлов. ZIP содержит **все готовые файлы**, включая отчёт. Не предоставлять отдельную ссылку на PDF, если пользователь не попросил.

## Шаблон краткого отчёта по запуску

```text
Статус: завершено / обработано частично / заблокировано
Исходник: название, SHA-256, всего N страниц
Выполнено: реальные диапазоны страниц; режимы A/B/C/D
Проверено: диапазоны/выборка, что именно протестировано
Навигация: готово / в работе; число закладок и внутренних ссылок
Паспорт: XMP записан/пропущен, версия, статус, метод, отметка placed/omitted_*; SHA-256 финального PDF — в отчёте
Сложные участки: страницы и причины неопределённости
Созданные файлы: фактически существующие имена в ZIP
Продолжение: какой файл приложить и какое действие потребуется
Предложения для проекта: имеется / нет
```

Если обработана часть, честно написать: **«Обработка книги выполнена частично. Готовы страницы X–Y из N [или перечислены несколько диапазонов]. Промежуточный результат сохранён в ZIP-архиве. Чтобы продолжить, напишите „Продолжай“».** Только если ZIP реально создан и проверен. Не выдавать «следующая страница 201», если остались дыры раньше.

## Проверка ZIP перед передачей

- Проверить точный путь и существование архива, его размер, возможность открыть и прочесть записи.
- Убедиться, что он содержит заявленные файлы и что PDF открывается; сверить контрольные суммы и данные `progress.json` с фактическим содержимым.
- Не включать неготовые версии как финальные; не выдавать ссылки, путь которых не подтверждён в текущей файловой среде.


## Машиночитаемый паспорт BookScan: версия схемы 1

**Назначение:** оперативно обнаруживать ранее обработанную книгу, не запускать OCR без оснований, хранить проверяемый контекст работы. Рекомендуемый носитель — **XMP PDF** в отдельном пространстве имён, например `urn:bookscan:processing:v1#`, а не основное заглавие/автор документа и не видимый текст страницы. Достаточно одного актуального паспорта. Если библиотека не умеет корректно писать XMP, не имитировать запись: отметить это в отчёте. Не создавать пустой «completed».

**Рекомендуемые поля (пример структуры данных, не утверждение о выполненной работе):**

```json
{
  "schema_version": 1,
  "producer_tag": "BookScan",
  "project_rules_version": "1.1.0",
  "processing_status": "completed",
  "completed_at_utc": "YYYY-MM-DDTHH:MM:SSZ",
  "source_sha256": "<действительный SHA-256 исходного PDF>",
  "source_page_count": 500,
  "output_page_count": 500,
  "methods": ["A", "B"],
  "text_qa": {"scope": "sampled", "warnings": 0},
  "toc_qa": {"links_technical_checked": 120, "bookmarks_checked": 123},
  "tool_versions": {"pymupdf": "<если использовался>", "tesseract": "<если использовался>"},
  "visible_mark": "placed"
}
```

- Даты, версии, SHA-256, результаты и числа **подставлять только фактические**. Неизвестные необязательные поля не заполнять выдумками. В XMP помещать компактные проверяемые технические сведения, без фрагментов книги, личных данных и конфиденциальных имён файлов.
- Поля `processing_status=completed` и `completed_at_utc` присваивать **только после** полной сборки и обязательного контроля из `03_QUALITY_AND_TOC.md`; черновику/пакету нельзя присваивать такой паспорт.
- Паспорт может быть изменён третьими лицами. Без внешнего проверенного отчёта ZIP не обещать криптографического подтверждения происхождения. Для повторной загрузки сверять структуру, навигацию, несколько контрольных страниц и риски.
- `source_sha256` относится к **дообработанному** исходнику, не к итоговому файлу. Самохеширование: не записывать SHA-256 итогового PDF внутрь этого же PDF. После окончательного сохранения вычислить `final_sha256` и записать его **только в `report.md` итогового ZIP**; это позволяет проверить неизменность полученного файла при наличии отчёта.
- Фиксировать фактические версии OCR-движков/библиотек отдельно от `project_rules_version`. В новой редакции PDF обновлять/заменять прежний паспорт только при проведённой обработке и успешных тестах.
- Если пользователь повторно передал уже обработанную книгу, не выпускать «новый финальный файл» только ради нового номера версии и метки. Диагностика без OCR остаётся первым шагом.

### Порядок финализации без ложного статуса

1. Проверить всю необходимую обработку, открыть PDF, проверить страницы и навигацию.
2. На **копии** внести XMP-паспорт, затем при допустимости — одну фиксированную видимую метку на последней странице (см. `03_QUALITY_AND_TOC.md`). Не менять видимую область при занятом месте.
3. Сохранить PDF; повторно открыть и проверить, что метаданные читаются, нет более одной метки, не нарушены ссылки и изображения. Если для XMP/метки пришлось отступить от требований целостности — откатить операцию и перечислить ограничение.
4. Только по фактически сохранённому результату вычислить `final_sha256`, сформировать `report.md` с результатами и пропусками, собрать ZIP.
5. Проверить содержимое ZIP, CRC, читаемость и соответствие `final_sha256` реальному PDF внутри ZIP. Не передавать одиночный PDF.

**Учёт неполного результата:** промежуточный ZIP хранит `progress.json`, методы, версии и предупреждения, но не «completed» в финальном PDF. Отсутствие паспорта в частичном блоке — норма.
